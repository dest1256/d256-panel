# d256 — архитектура (черновик для утверждения)

Статус: **черновик этапа 1. Реализация не начата.** Документ описывает, как из 3x-ui получаются два сервиса:
`d256-panel` (веб-панель, единственная БД) и `d256-node` (консольный демон с встроенным xray-core).

Основа форка: **3x-ui v3.11.0** (последний релизный тег; `main` на момент анализа — `83ea59f`, нестабильный).
Модуль апстрима: `github.com/mhsanaei/3x-ui/v3`, Go 1.27.3, xray-core `v1.260327.1-0.20261021115930-1b1647cd9ddf` (go.mod тега v3.11.0).
Всё ниже про апстрим проверено по исходникам этой версии (пути в `internal/...`), а не по памяти.

## 2. Раскладка по репозиториям

### d256-panel (форк 3x-ui)
**Остаётся:** UI и навигация, тёмная тема, RU/EN, пользователи/сессии/2FA/CSRF/API-токены, inbounds/clients/groups/hosts, роутинг и
аутбаунд-шаблоны (как данные, см. §4.3), подписки (`internal/sub`), боты уведомлений/LDAP (если выберем «оставить»), серверный
`Setting`, метрики самой панели.

**Удаляется:**
- запуск/останов/логи локального Xray (`xray/process.go`, `check_xray_running_job`, `XrayLogModal`, «Версия Xray»/обновление ядра на панели);
- `runtime.Local`, `runtime.Remote` + `tls_client.go`, `service/node*.go` (HTTP-sync), `inbound_node.go`, `node_*_job`, baseline/GUID/dirty-логика,
  таблицы `NodeClientTraffic`, `NodePendingReset`, `NodeClientIp`, `ClientGlobalTraffic` (заменяются схемой §6);
- `xray_traffic_job`, `check_client_ip_job` (fail2ban/лог-парсинг) — трафик и IP теперь приходят от узлов;
- sidecar-движки внутри панели (MTProto/TUIC/AmneziaWG) — по ответу на вопрос A.

**Добавляется:** gRPC-сервер для узлов (mTLS), внутренний CA, enrollment, `NodeHub` (сессии узлов в памяти), сборщик желаемого
состояния на узел, приёмник журнала/статистики, хранилище соединений, страницы «Узлы»/дашборд/«i» клиента.

### d256-node (новый, не форк-дерево)
Один бинарник `d256-node`: CLI + демон. Go-код с нуля (≈ 5–8 тыс. строк), зависимости: `xray-core` (библиотека, **та же версия**,
что у панели), `grpc`, `gopsutil`, `bbolt` (или SQLite), AEAD из `x/crypto`. Из 3x-ui берётся только идея `hot_diff` (переписывается под
in-process API) и GPL-лицензия/атрибуция.

### Общий контракт
`d256-panel/proto/` — `.proto` + сгенерированный Go-код как **отдельный Go-подмодуль** `github.com/dest1256/d256-panel/proto`
(свой `go.mod`, теги вида `proto/v0.1.0`). Узел делает `go get …/proto@v0.1.0`.
Почему не submodule: обычный `go.mod` версионируется, воспроизводится в Docker-сборке без `git submodule update`, не ломает `go mod vendor`.
Генерация (`protoc`, `protoc-gen-go`, `protoc-gen-go-grpc`) — только в dev-контейнере через `make proto`.
Предполагаемый GitHub-неймспейс — `github.com/dest1256` (поправь, если другой).

## 3. Протокол панель ↔ узел

### 3.1 Транспорт
- **gRPC поверх mTLS**, узел — клиент (исходящее соединение), один двунаправленный стрим `NodeLink.Connect(stream NodeToPanel) returns (stream PanelToNode)`.
- Keepalive gRPC + прикладной heartbeat (каждые 5 с, из него считается задержка RTT). Переподключение с экспоненциальной паузой + jitter.
- Лимиты: `MaxRecvMsgSize` 4 МиБ для сообщений от узла, rate-limit по узлу, deadline на unary.
- **Предлагаемое размещение относительно Caddy** (вопрос C): Caddy проксирует веб-UI и `POST /enroll` (публичный сертификат).
  gRPC-порт (по умолчанию `:8444`) панель слушает **сама**, mTLS заканчивается в процессе панели (end-to-end, без доверия к заголовкам Caddy),
  серверный сертификат — из внутреннего CA (узел пиннит CA при enrollment).

### 3.2 Enrollment и PKI
1. Панель при первом старте создаёт **внутренний CA** (ECDSA P-256, ключ шифруется мастер-ключом панели, хранится вне публичных путей).
2. «Узлы → Добавить»: создаётся запись узла (`status=pending`) и **одноразовый токен** (256 бит, в БД только SHA-256-хэш, TTL 1 ч, одно использование).
   UI показывает готовую команду `d256-node enroll https://panel.example.com <token>` (токен — только один раз).
3. Узел генерирует ключевую пару **локально** (приватный ключ не покидает узел), шлёт `POST /enroll {token, csr, hostname, versions}` по HTTPS
   (проверка по системным корням). Панель атомарно «сжигает» токен, подписывает CSR (клиентский сертификат на 90 дней, SAN URI
   `d256://node/<node_id>`), возвращает сертификат, CA, адрес gRPC и `node_id`.
4. Ротация: узел за 30 дней до истечения присылает новый CSR по уже установленному mTLS-каналу.
5. Отзыв: удаление узла / «Отозвать» → серийник в denylist (проверка при рукопожатии и на каждом стриме).
6. Идентификация: `node_id` берётся **только из проверенного сертификата**, никогда из тела сообщений.

### 3.3 Сообщения (эскиз)
`NodeToPanel` (oneof): `Hello{proto_version, node_version, xray_version, os/arch, applied_state_version, journal_head_seq}`,
`Heartbeat{ts}`, `SystemMetrics{cpu, ram, swap, disk, net, tcp_sockets, udp_sockets, uptime}`, `XrayStatus{state, error}`,
`StateAck{version, ok, error}`, `ActiveConnections{snapshot}`, `JournalBatch{records[], from_seq, to_seq}`, `CommandResult{...}`.

`PanelToNode` (oneof): `HelloAck{accepted, min_proto, reason}`, `DesiredState{version, xray_config_json, client_limits[], settings}`,
`JournalAck{acked_seq}`, `Command{reload | restart | reset_client_traffic | update_geo | get_logs}`.

**Совместимость:** `proto_version` — целое число; панель в `HelloAck` сообщает минимально поддерживаемое, при несовпадении узел
получает `accepted=false` + понятную причину и остаётся в режиме «работаю по кэшу». Добавление полей — обратно совместимо (proto3).

### 3.4 Желаемое состояние
- Панель — единственный сборщик: для узла N она строит **полный Xray JSON** (переиспользуем `service/xray.go: GetXrayConfig`, фильтруя
  inbounds по узлу и подставляя шаблон роутинга/аутбаундов узла, §4.3) и **снимок лимитов клиентов** (квота, уже использовано, срок, лимит устройств).
- `version` — монотонный номер на узел (счётчик в БД, растёт при любом изменении, затрагивающем узел). Панель шлёт состояние при подключении
  и при каждом изменении (с дебаунсом ~500 мс).
- Узел применяет **атомарно**: (1) разбор и `core.New(config)` для проверки без запуска; (2) diff со старым конфигом: добавить/убрать
  inbound, добавить/убрать пользователя — **in-process** через `inbound.Manager`/`proxy.UserManager` без обрыва соединений; (3) всё остальное
  (routing, outbounds, DNS, изменение транспорта) — пересоздание экземпляра core с перезапуском; (4) при ошибке старта — откат на предыдущий
  экземпляр и `StateAck{ok:false,error}`; (5) только после успеха запись в кэш и `StateAck{ok:true}`.
  Соединения при «тяжёлых» изменениях рвутся — как и в апстриме; пользователь видит это в UI («требуется перезапуск»).

## 4. Xray на узле и учёт соединений

### 4.1 Xray как библиотека
Узел: `core.New(cfg)` + `Start()`. Конфиг JSON → `*core.Config` тем же `infra/conf`, что и в апстриме. Версия xray-core фиксируется в обоих
`go.mod` одним значением; узел в `Hello` сообщает её, панель показывает. Обновление Xray = новый релиз `d256-node` (кнопка «обновить Xray» на панели
исчезает; вместо неё — «обновить geo-файлы» командой узлу).

### 4.2 Трафик по соединениям без патча xray-core
Проверено по исходникам: `routing.Dispatcher` — публичный интерфейс (`xray:api:stable`, `features/routing/dispatcher.go`):
`Dispatch(ctx, dest) (*transport.Link, error)` и `DispatchLink(ctx, dest, link) error`. `DefaultDispatcher` (`app/dispatcher/default.go`) создаёт
`*transport.Link` для клиента, а сниффинг/маршрутизация выполняются асинхронно и **пишут итоговый адрес в общий `*session.Outbound`**
(`ob.Target`, `ob.Tag`), который доступен через `session.OutboundsFromContext(ctx)`.

План без патча:
1. Собственный `Dispatcher`, внутри которого — стандартный `DefaultDispatcher` (создаётся через `common.CreateObject`).
2. `Dispatch`/`DispatchLink`: вызываем внутренний, берём из `ctx` `session.InboundFromContext` (email пользователя, тег inbound, **IP источника**,
   сеть), оборачиваем `Link.Reader/Writer` счётчиками байт up/down.
3. При закрытии link читаем `ob.Target` (домен после сниффинга или IP), `ob.Tag`, время — формируем запись соединения.
4. Подмена фичи: `infra/conf` всегда добавляет `dispatcher.Config` в список app; мы **удаляем его из собранного `*core.Config`** перед `core.New` и
   добавляем свою фичу тем же типом (`routing.DispatcherType()`). **Это нужно проверить прототипом на этапе 6** (риск: порядок инициализации
   `core.RequireFeatures`). Если не выйдет — запасной вариант: зарегистрировать собственный `common.RegisterConfig` с типом-сообщением и вставить
   его вместо дефолтного. Патч исходников xray-core **не планируется**; если прототип покажет, что без него нельзя, остановлюсь и спрошу.
5. Сниффинг домена требует `sniffing.enabled` на inbound. Для учёта доменов панель принудительно включает sniffing (`destOverride` http/tls/quic)
   на узловых inbound или показывает предупреждение (решим на этапе 6; влияет на поведение для пользователей).

Это же место — единственный точный источник «онлайн + IP источника» и принудительного лимита устройств (§7): новое соединение с (N+1)-го IP
отклоняется в нашем `Dispatch`, без fail2ban и парсинга access.log.

### 4.3 Привязка сущностей к узлам (модель данных конфигурации)
- Inbound: поле `NodeID` уже есть в апстриме (1 inbound → 1 узел, `NodeID=NULL` больше не допускается — «локальный» Xray убран). Вопрос B: нужно ли M:N.
- Клиенты привязаны к inbound'ам (таблица `ClientInbound`), значит, неявно к узлам.
- Xray-шаблон (routing, outbounds, dns, policy): в апстриме один глобальный (`Setting.xrayTemplateConfig`). Добавляем таблицу
  `node_xray_templates(node_id NULL=по умолчанию, template_json)`; узел использует свой шаблон, иначе глобальный. UI «Xray-настройки» получает селектор узла.
- Hosts (переопределение адреса в подписке) — как в апстриме; адрес по умолчанию для inbound'а — домен узла (поле `Node.Address`/`PublicHost`).

## 5. Подписки
`internal/sub` остаётся в панели. Меняется только то, что «адрес сервера по умолчанию» берётся из публичного хоста **узла inbound'а**,
а не из адреса панели. Форматы и ссылки не меняются; golden-тесты `internal/sub` остаются как регрессия.

## 7. Офлайн-режим и журнал

**Хранение на узле** (оба файла шифруются AEAD, ключ — §9):
- `state.cache` — последний `DesiredState` + сертификаты;
- `journal.db` — bbolt (одна append-only бакет-очередь, ключ = `seq` big-endian).

**Журнал и `seq`:**
- Каждая запись (дельта трафика клиента, закрытое соединение/агрегат, снимок онлайн-IP, событие) получает монотонный `seq` из счётчика,
  который хранится в журнале и переживает рестарты.
- Онлайн: записи отправляются сразу, лежат в памяти до `JournalAck` (в диск не пишутся). При потере связи неподтверждённый хвост + новые записи
  уходят в `journal.db`. Допущенное окно потерь: при аварийном падении узла **в онлайне** теряется неотправленное за последний интервал flush (≤ 5 с трафика) —
  это записано как известное ограничение (альтернатива — писать всё на диск всегда, но ТЗ говорит «только когда связи нет»).
- При переподключении: `Hello.journal_head_seq` → панель отвечает ожидаемым `acked_seq`; узел шлёт пачки (≤ 1000 записей / 1 МиБ) подряд.
- **Идемпотентность:** панель хранит `nodes.journal_acked_seq`. Пачка применяется **в одной транзакции** вместе с обновлением `journal_acked_seq`,
  принимается только если `first.from_seq == acked+1` (сжатые записи несут диапазон `[from_seq,to_seq]`); повтор уже принятой пачки — no-op с тем же ACK.
  Разрыв → NACK с ожидаемым seq, узел пересылает с него.
- **Переполнение:** лимит журнала (по умолчанию 256 МиБ). При достижении 80 % — компактор объединяет самые старые записи в **часовые агрегаты**
  (клиент × назначение × час; трафик суммируется, ничего не отбрасывается; запись получает диапазон seq). Если и агрегаты не влезают — алертим и
  останавливаем запись детализации по назначениям (оставляем только дельты трафика по клиентам — они мизерные), событие в `status`/UI.

**Ограничения клиентов офлайн:** узел из `client_limits` ведёт локальный остаток (квота − использовано на момент снимка − локальные дельты), срок,
лимит устройств. Исчерпал — пользователь удаляется из работающего Xray in-process, событие в журнал. **После переподключения приоритет у панели:**
сначала журнал (панель досчитывает трафик, может отключить клиента сама), затем узел принимает свежий `DesiredState` с версией выше своей.

## 8. UI

Все экраны расширяют существующие страницы (`frontend/src/pages/...`):
- **Дашборд** (`index/`): переключатель «Все узлы | <узел>»; карточки статуса, CPU (ядра/частота/загрузка), RAM/swap/диск, сеть, TCP/UDP сокеты,
  онлайн-клиенты, размер журнала, версии; графики из `node_metrics` (периоды как сейчас); блок метрик самой панели.
- **Узлы** (`nodes/`): форма «Добавить» → токен + команда enrollment, статус/задержка/последний контакт, отзыв сертификата, команды reload/restart.
- **Клиент → «i»** (`ClientInfoModal.tsx` расширяется): график трафика (1ч/24ч/7д/30д/произвольно, разбивка по узлам и inbound'ам), активные
  соединения (автообновление по WS), таблица доменов/IP за период (сортировка, поиск, фильтр по узлу, экспорт CSV), IP устройств.

## 9. Безопасность

**Защищённый режим узла (шифрование с внешним ключом, ввод пароля при запуске) по решению заказчика не делается.** Кэш и журнал на узле
по-прежнему зашифрованы (XChaCha20-Poly1305), но ключ выводится из приватного ключа узла, лежащего на том же диске, — это защита от подмены
и случайного чтения, а не от человека с доступом к диску. Узел следует ставить на сервер, которому доверяют. Секреты (токен enrollment) не пишутся в логи.

- Панель: rate-limit и lockout на enrollment, одноразовые токены, CSRF/сессии апстрима сохраняются, node_id только из сертификата,
  валидация всего от узла (неизвестный email/inbound → отбрасывается и логируется, отрицательные/нереалистичные дельты отбрасываются, лимит размера сообщений).
  Подделку статистики **своим** узлом предотвратить нельзя (он контролирует свои данные), но он не может писать данные за чужие узлы и клиентов,
  не привязанных к нему.

## 14. Отклонения от плана, выявленные в этапе 3 (реализовано)

- **Отзыв сертификата** без отдельной таблицы `node_revoked_certs`: канал принимает только сертификат, чей серийник записан в `nodes.cert_serial`.
  Повторная регистрация/«Новый токен»/удаление узла меняют серийник, и действующий сеанс закрывается (проверка при подключении и каждые 30 с).
- **Регистрация** — `POST {basePath}/d256/enroll` (JSON, вне сессий/CSRF, лимит 10 попыток/мин на IP и 120/мин всего, тело ≤ 64 КиБ).
  Токен имеет вид `<node_id>.<секрет>`; в БД только SHA-256 секрета; погашение атомарное (`UPDATE … WHERE used_at=0 AND expires_at>now`).
  Некорректный CSR токен не сжигает. Узел в `enroll` читает токен из stdin (`-`), чтобы он не попадал в `argv`.
- **Серверный сертификат gRPC** выпускается внутренним CA для имён, с которых узлы регистрировались (Host запроса или `webDomain`);
  узел проверяет сервер только по CA панели (пиннинг), `MinVersion` TLS 1.3.
- **Метрики узла**: сообщение `SystemMetrics` каждые 5 с; панель кладёт их в существующие поля `Node` и историю `nodeMetrics`
  (cpu/mem/netUp/netDown), а полный снимок (ядра, частота, swap, диск, сокеты, клиенты онлайн, журнал) держит в памяти `Hub` и отдаёт по `GET /panel/api/nodes/live`.
  После перезапуска панели «живые» подробности появляются, когда узел переподключится (это ≤ 60 с).
- **RTT** измеряет узел (эхо `Heartbeat`) и сообщает в следующем heartbeat (`last_rtt_ms`).
- Старые HTTP-джобы heartbeat/traffic-sync отключены; их код и модель старого multi-node удаляются в этапе 4.
- Языки интерфейса сокращены до `ru-RU`/`en-US`.

## 15. Этап 4: что реализовано и что осталось

Реализовано (проверено сквозным тестом `deploy/smoke/smoke.sh`: панель + узел + Xray-клиент с реальным трафиком):
- **Конфиг на узел.** `XrayService.GetXrayConfigForNode(id)` собирает Xray JSON только из inbound'ов этого узла и вырезает локальную обвязку (`api`, `metrics`, файлы логов, inbound `api`).
  Версия `desired_version` растёт только при реальном изменении конфига (SHA-256), панель пересчитывает каждые 2 с и сразу отправляет изменения. Состояние — чистая функция БД, поэтому отдельных «dirty»-флагов нет.
- **Применение на узле** (`d256-node/internal/xrayrun`): xray-core как библиотека; новый конфиг сначала разбирается, при ошибке старта восстанавливается предыдущий; счётчики трафика не теряются при перезапуске.
  **Без перезапуска** применяются: добавление/удаление/замена пользователя и добавление/удаление inbound'а. План строит панель существующим алгоритмом `ComputeHotDiff` и шлёт готовые операции (`HotOp`, пользователь — как готовый `protocol.User`);
  если операция не прошла или база плана не совпадает с применённой версией — полный перезапуск с полным конфигом.
  Настройка «перезапускать Xray при отключении клиента» (чтобы оборвать живые сессии) соблюдается.
- **Трафик.** Узел раз в 5 с отправляет `TrafficBatch` (дельты по клиентам и inbound'ам) с диапазоном `[from_seq,to_seq]`. Панель принимает пачку только при `from_seq == acked+1` и в **той же транзакции** обновляет `nodes.journal_acked_seq`
  вместе с `InboundService.AddTrafficTx`, так что повтор не считается дважды. Имена вне узла (чужие клиенты, неизвестные теги) отбрасываются. Новая эпоха узла (`journal_epoch`) обнуляет позицию.
- **Онлайн.** Узел шлёт в `XrayStatus.online_users` список email'ов с живыми соединениями; панель отдаёт их как «онлайн».
- **Подписки.** `internal/sub` без изменений: адрес берётся из узла inbound'а (`Node.Address`).
- **Вырезано** (по ответу A и по решению о локальном Xray): локальный Xray и его задачи/эндпоинты/логи, HTTP-синхронизация и проверка старых узлов, mTLS старой схемы, Telegram/Discord/e-mail, LDAP, WARP/Nord/PIA, MTProto, AmneziaWG, sponsors, tunnelmonitor, fail2ban-статус.
  Тесты, которые проверяли только это, удалены; остальные сохранены (в т.ч. golden-тесты подписок).

Осталось в рамках этапа 4 (вынесено, чтобы не держать этап):
- **4e. TUIC на узле.** TUIC остаётся в продукте (решение пользователя), но его движок (`internal/tuic`) пока не запущен на узле: создание TUIC-inbound'а через API временно отклоняется с понятным сообщением.
  План: вынести `internal/tuic` в общий Go-подмодуль, передавать параметры TUIC-инстансов в `DesiredState`, запускать менеджер на узле, учитывать его трафик в `TrafficBatch`.
- **Шаблоны Xray по узлам** (`node_xray_templates`, раздел 4.3): пока все узлы используют глобальный шаблон роутинга/аутбаундов.
- **Остатки настроек:** поля LDAP/Telegram/SMTP/Discord ещё есть в модели настроек и на вкладке «Общие» — не работают и подлежат удалению; код локального жизненного цикла Xray (`internal/xray/process.go` и т. п.) больше не вызывается из панели и подлежит удалению.
- Все утверждения о горячем применении проверены тестами узла (`xrayrun`) и сквозным тестом; нагрузочных проверок не проводилось.

## 16. Этап 5: офлайн-режим узла (реализовано)

Проверено сквозным тестом: панель остановлена, через узел идёт трафик, узел пишет его в журнал на диск (`journal: 103 bytes`), панель поднимается, журнал доставляется и учёт сходится **ровно** (6 запросов = 6 × 1011 байт, журнал после подтверждения пуст).

- **Хранение** (`d256-node/internal/vault`): XChaCha20-Poly1305, ключ — HKDF от приватного ключа узла.
  Каждый блок привязан к назначению («journal/batch», «cache/state»): блок журнала нельзя подсунуть как кэш. Подмена и чужой ключ обнаруживаются.
- **Кэш состояния** (`cache.bin`): последний `DesiredState` + снимок лимитов, запись атомарная. При старте узел сразу поднимает Xray из кэша, не дожидаясь панели (проверено перезапуском демона без панели).
- **Журнал** (`journal.db`, bbolt): пишется **только при отсутствии связи** и при корректной остановке (сброс очереди из памяти). Пока связь есть, пачки живут в памяти до `JournalAck`.
  Нумерация монотонна внутри эпохи; эпоха и следующий `seq` сохраняются только при чистом закрытии. После аварийного завершения начинается **новая эпоха**, уцелевшие записи перенумеровываются с 1 — панель обнуляет позицию, а не считает новое использование «уже учтённым».
  Окно потерь: аварийное падение при живой связи теряет не более одного интервала (5 с) ещё не отправленного использования.
- **Досылка и идемпотентность.** При подключении узел поднимает записи из журнала и шлёт их по порядку; панель применяет пачку один раз (см. §15), узел удаляет подтверждённое из памяти и с диска. Если подтверждение отстаёт от отправленного — отправка продолжается с позиции панели.
- **Переполнение.** Лимит журнала (по умолчанию 256 МиБ). При 80 % самые старые записи сливаются по часам (в одну запись суммируются байты по именам), затем, если надо, независимо от часа, до 50 %. Трафик не отбрасывается, теряется только временное разрешение. Покрыто тестом (400 записей при лимите 4 КиБ: суммы и диапазоны `seq` без разрывов).
- **Лимиты клиентов офлайн** (`internal/limits`): панель шлёт `LimitsSnapshot` (квота, использовано, срок) при подключении и раз в минуту. Без связи узел прибавляет измеренное использование к последнему снимку; при превышении квоты или истечении срока перезапускает Xray без этого клиента (живые сессии обрываются).
  После переподключения **приоритет у панели**: первое `DesiredState` применяется полностью и возвращает всех, кого панель всё ещё разрешает (проверено).
  Допущение: использование, уже отправленное, но ещё не подтверждённое в момент снимка, может быть учтено дважды — ошибка в сторону более раннего отключения, не более одного интервала.
  **Лимит устройств** офлайн применяется узлом по IP источников (§17).

## 17. Этап 6: учёт подключений и информация о клиенте (реализовано)

Проверено сквозным тестом (`deploy/smoke/smoke.sh`): запрос через узел появляется в «Доменах и IP» (`example.com`, tcp, 150/1872 байт, 2 соединения), удерживаемое соединение видно как активное с IP источника и именем узла, устройство попадает в список, серия графика строится по узлу, CSV выгружается; после этого офлайн-журнал по-прежнему доставляется ровно один раз.

- **Перехват без патчей xray-core** (`d256-node/internal/connstats`): запись `dispatcher.Config` в `core.Config.App` подменяется несущим сообщением, зарегистрированным через `common.RegisterConfig`; его создатель строит штатный диспетчер и оборачивает его в `Tracker`. Маршрутизация, fake DNS и sniffing не меняются. Для каждого соединения со стороны входа считаются байты (запись = отдача клиента, чтение = загрузка; для `DispatchLink` наоборот), назначение берётся как `RouteTarget` → результат sniffing → адрес запроса. Обёртки пробрасывают `Interrupt`/`Close`/`ReadMultiBufferTimeout`.
- **Что хранит узел:** живые соединения (клиент, inbound, IP источника, назначение, порт, сеть, старт, байты) и агрегаты клиент × назначение × inbound × сеть × час. Долгие соединения сливаются в агрегат постепенно, а не по закрытию. Список устройств (IP за последние 30 минут) ограничен 50 на клиента; снимок живых соединений — 5000.
- **Что шлёт узел:** раз в интервал — `ActiveConnections` (снимок, заменяется целиком) и агрегаты закрытого в составе `TrafficBatch.conns`. Агрегаты едут тем же журналом, что и байты по клиентам: попадают в офлайн-журнал, сливаются по часам при сжатии и применяются панелью в той же транзакции, что и позиция журнала, — то есть ровно один раз.
- **Что хранит панель:** `conn_stats_hourly` (узел × клиент × inbound × назначение × сеть × час, upsert со сложением), `conn_stats_daily` (то же по дням), `traffic_buckets` (5-минутные корзины клиента/inbound для графиков). Индексы по `(email, hour)` и `(email, dest)`. Приём проверяет: клиент и inbound принадлежат этому узлу, сеть tcp/udp, назначение без управляющих символов и ≤ 253 байт, час в разумных пределах, размеры не переполняют int64; дубликаты ключа в одной пачке складываются.
- **Хранение (настраивается окружением):** часовые строки `XUI_CONN_RETENTION_DAYS` (30) сворачиваются в дневные и удаляются; дневные живут `XUI_CONN_DAILY_RETENTION_DAYS` (365); 5-минутные корзины старше 48 ч сворачиваются в часовые, часовые живут `XUI_TRAFFIC_RETENTION_DAYS` (90). Задача идёт раз в час и при старте, идемпотентна.
- **API** (`/panel/api/clientInsights/*`, email в query): `connections`, `devices` (из последних снимков узлов в памяти панели; снимок старше 30 с не показывается), `destinations` (период, узел, поиск, сортировка, `format=csv` с защитой от формул), `traffic` (ряды по узлам и по inbound). Поиск экранирует `%` и `_`.
- **UI:** кнопка в окне информации о клиенте открывает окно с вкладками «Трафик» (отдача/загрузка, период 1ч/24ч/7д/30д/свой, разбивка по узлам или inbound), «Активные подключения» (обновление раз в 3 с), «Домены и IP» (сортировка, поиск, фильтр по узлу, CSV), «Устройства».
- **Лимит устройств:** панель отдаёт `ClientLimit.device_limit` (из `limit_ip`) в `LimitsSnapshot`. Узел допускает новое соединение, только если его IP уже среди активных соединений клиента или различных активных IP меньше лимита; иначе соединение отклоняется. Работает и без панели (лимиты лежат в кэше). Проверено тестом с реальным клиентом: тот же адрес допускается, второй — нет, после ухода первого — допускается.

Известные ограничения:
- Разбивка графика по inbound берётся из часовых строк назначений, поэтому для неё минимальный шаг — час.
- Список устройств и активные соединения живут в памяти панели: после её перезапуска пусты до первого снимка узла (до нескольких секунд).
- Лимит считает **одновременно активные** IP; клиент, переключающий сети, не вытесняет сам себя, пока старое соединение не закрылось.
- Для UDP «соединение» — это поток диспетчера Xray, а не сокет.
